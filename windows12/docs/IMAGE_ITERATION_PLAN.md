## Recommendation and scope

A small desktop-overlay update can plausibly reuse the completed live chroot, avoiding another KDE bootstrap/package transaction. This applies only after the first ISO and checksum have been exported successfully and the builder VM is confirmed stopped. Keep its first candidate and evidence even if its GUI needs fixes. Do not interrupt a current download to try this path.

The smallest conservative stage sequence is: update the package-managed overlay in the retained target; regenerate package/file manifests; clean binary output; regenerate the installer stage explicitly; rebuild the binary stage. It is **not** simply `lb clean --binary; lb binary`: that deletes installer files while retaining their completed stage flags in the reviewed version. Remaining installer/build-tool downloads and full SquashFS compression/ISO assembly can still take substantial time. No fixed speedup or offline rebuild is promised.

Limit the first experiment to assets/configuration/launcher changes with unchanged dependencies, kernel, boot configuration, installer policy and target package set. Dependency changes require a larger reviewed rebuild. Existing-user Plasma migration is not established by changing `/etc/skel` or first-login layout defaults.

## SquashFS compression and future iteration cost

In the same exact source, `scripts/build/binary_rootfs` lines 313–323 selects `-comp xz` when `LB_CHROOT_SQUASHFS_COMPRESSION_TYPE` is empty. A configured type becomes `-comp <type>`; a configured level becomes `-Xcompression-level <level>`. The current recipe specifies neither. It also adds `-no-progress` for non-TTY stdin (lines 285–290), so a quiet compression phase is not itself a hang. With the default chroot build it invokes `nice -n 17 mksquashfs chroot filesystem.squashfs ...` (line 336).

Therefore the expected algorithm is **xz**, subject to confirming the actual installed source/configuration. No explicit compression level, block size or processor count is selected by this recipe; tool defaults and any effective configured options must be recorded from the real build before making performance claims. Compression under TCG could become expensive, but it has not yet been measured in this candidate.

The documented configuration controls are `lb config --chroot-squashfs-compression-type <supported-type>` and `--chroot-squashfs-compression-level <supported-level>`. For a separately identified future iteration, evaluating another supported algorithm such as zstd may be reasonable. Check the actual target mksquashfs help for algorithm-specific level support rather than assuming every algorithm accepts the same tuning flags. Preserve all saved build options and source provenance; do not edit a running build or silently change the current candidate's compression. Any algorithm change requires a newly hashed image and actual kernel/initramfs boot test, plus a size/time comparison. It is an optional engineering experiment, not a chosen distribution policy.

## Controlled implementation proposal

This is a design sequence for a future bounded implementation, **not a command to run on the host**. Every chroot/package/mount operation below occurs only inside the contained builder VM's disk.

1. **Establish the completed baseline.** Require host-verified ISO checksum, successful export marker, stopped recorded VM/QMP listener and released runner lock. Preserve candidate ISO, source tar/lock, package/deb hashes, manifests and logs under a candidate-specific project directory. Record the stopped disk's identity, backing chain and checksum. Check storage before duplicating anything.
2. **Preserve rollback state without a full live-disk copy.** A new project-contained qcow2 child of the completed, stopped builder disk is a plausible low-copy workspace; keep the parent immutable. This is not implemented by the current wrapper. Require exclusive ownership and validate the complete backing chain. If a safe separate iteration disk cannot fit or be supervised, stop rather than mutate the only preserved baseline. Never create a live backup by recursively copying a changing qcow2.
3. **Freeze a new iteration source.** Bump `windows12-desktop` from `0.1.0~preview1` to a strictly newer preview version. Make a new immutable archive/digest and source commit; retain the original `checks.tar` and lock unchanged. Record the baseline candidate, parent disk digest, new archive digest, package version, controller/guest-recipe hashes and intended changes. The current `--resume` deliberately reruns the old archive and cannot perform this update safely.
4. **Boot once with explicit iteration intent.** A future controller needs a validated iteration disk, fresh output directory, exact source map and new cloud-init instance ID. Refresh the current proxy/CA in the builder only. Serve the new archive through the existing exact-path HTTP mechanism, extract it to a new guest source directory, and never overlay it on the old guest source directory (removed source files could otherwise remain). The two-boot metadata probe supports feasibility; actual image iteration remains untested.
5. **Inspect before modification.** Inside that VM confirm `/run/windows12-build-vm`, the exact live-build version, expected build directory, installed old overlay version, a clean/retained target at `/root/windows12-build/chroot`, no nested installer/binary chroot left behind and no active prior lb job or preparation mounts. Inspect `.build`, saved configuration, manifests, `cache/bootstrap` and `LB_CACHE_STAGES`. Require no stale rootfs cache to be selected. `installer_chroot` copies `cache/bootstrap` in the reviewed default path; its availability is a hard precondition, not something to discover after deleting output.
6. **Build and install the new overlay locally.** Run the new snapshot's unit gates and deterministic double packaging in the VM. Inspect its control/dependency metadata and compare dependency fields to baseline; reject changed dependencies for this small-update path. Retain the old .deb and place only the new overlay version in the iteration build's local package configuration. Prepare only the needed chroot helpers/service-start policy using the matching live-build version. Copy the reviewed .deb into the contained target and use target `dpkg -i` so its database and owned-file removals update normally. Do not unpack source files manually over managed paths or run a broad APT upgrade. Resolve any conffile prompt using an explicit reviewed policy; a pristine baseline should be verified before choosing new defaults.
7. **Repeat the project's target validation/cleanup.** Execute the reviewed `0990-remove-proxy.hook.chroot` logic inside the prepared target: known transient APT proxy/CA removal, desktop-entry validation and Python compilation. Do not force every upstream hook blindly; not all hooks are necessarily idempotent. Verify the new installed overlay version and managed file contents/modes; remove the staged .deb and temporary hook from the target, then undo only preparation helpers applied for this operation.
8. **Refresh manifests without erasing install/live distinctions.** Capture the target's actual `dpkg-query -W` as the new `chroot.packages.live` and regenerate `chroot.files` with the same target listing convention used by the matching `lb chroot`. Preserve the previous `chroot.packages.install` membership and replace only its overlay version record when that package was already an install-stage member. Do not replace the entire install list with the live list: the difference controls live-installer package removal. Require the package-set diff to contain only the intended overlay version change, or stop for review.
9. **Reassemble all affected media content.** Only after candidate preservation and chroot checks, run `lb clean --binary` inside the iteration VM. Then regenerate the installer explicitly using the reviewed equivalent of `lb installer --force`, followed by `lb binary`; do not assume old installer flags or cached rootfs imply fresh contents. Record cache hits, downloads and elapsed time. The installer stage can retrieve packages/indices; keep TLS/signature checks enabled and record actual mutable inputs. Full `lb build --force` is unnecessary and could redo expensive stages. After binary assembly, verify no temporary build proxy/CA leaked again.
10. **Export as a distinct candidate and validate.** Use new output paths and checksums, preserving the first candidate. The current controller's fixed artifact directory and rename behavior need a small explicit iteration-mode extension before this is runnable; never overwrite the original outputs as a shortcut. Audit the new ISO against the new archive, confirm both installer and live boot files, run actual boot/desktop/disposable installation checks, and compare all package/managed-file evidence. A successful `lb binary` alone does not validate the image.

## Validation and rollback gates

The first measured iteration should be one harmless visible overlay change plus version bump with identical dependencies. Acceptance requires: no KDE/bootstrap reinstall in logs; new package/version in target, exported manifests and ISO; unchanged unrelated target package versions; installer files and boot entries retained; matching frozen-source audit; repeatable boot and installed-disk results; and a measured storage/time report. Network traffic may remain for binary/installer tools and mutable repository metadata.

If any step fails, retain the iteration disk/output and error logs and leave baseline disk/ISO/source unchanged. Do not “roll back” by force-downgrading the only target or reusing a failed output directory. Start a separately identified iteration from the unchanged stopped baseline only after its failure is understood. If chroot state, bootstrap cache, matching tools or enough storage are absent, an ordinary clean rebuild remains the honest fallback; do not silently manufacture stage flags or trust stale manifests.

No iteration controller, guest recipe or rollback mechanism has been written for this plan. The immediate priority remains completing and validating the first candidate.
