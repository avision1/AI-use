# Contained build feasibility

Checked 2026-10-23 (America/Chicago). This is a source-build pipeline, not a completed release.

## Observed

- No initial QEMU, Podman/Docker, live-build, xorriso, squashfs utilities, or `/dev/kvm`.
- User namespace mapping is denied; bubblewrap namespace setup fails; Landlock returns ENOSYS. Do not use host chroot, host mounts, or globally installed packages as a fallback.
- Project-local QEMU dependencies were downloaded from Ubuntu 24.04 signed InRelease/Packages metadata. SHA256 checks protect each package; packages are unpacked, never installed. Python tar `data` filtering avoids unmapped UID/GID chown failures and external symlink targets. `build/tools-lock.json` records exact package versions, filenames and hashes.
- QEMU TCG firmware ran for ten seconds with no disk/network. Two BIOS attempts then stalled in an identical SMM handler; `smm=off` resolved the stall. Debian cloud guest subsequently booted Linux/systemd, grew its root filesystem to 20 GiB and ran cloud-init/our build script. This establishes real guest execution, not derivative desktop or installer success. The genericcloud kernel lacks 9p, so the initial output-share mount failed; the implementation now uses narrow HTTP artifact export instead.
- The execution environment assigns fresh loopback proxy ports to each tool invocation. Never hardcode a port copied from an earlier call. `build-vm.py` reads the current process HTTPS proxy and translates its loopback host to QEMU's host alias `10.0.2.2`.

## Build design

`python3 scripts/build-tools.py` prepares local QEMU tools on an amd64 Ubuntu 24.04 host. It reads the host Ubuntu archive verification key without changing it. It deliberately does not invoke apt install or run package maintainer scripts.

`python3 scripts/build-vm.py --probe` starts a diskless, networkless ten-second TCG process. The absence of KVM slows builds but does not preclude emulation.

`python3 scripts/build-vm.py --prepare` downloads Debian 13 genericcloud amd64 and checks SHA512 against the official HTTPS manifest. **Detached Debian image signatures are not yet verified**; this is HTTPS origin authentication plus transfer integrity, not an independently signed input chain. The tracked `build/builder-image.lock.json` pins build `20261021-2638`, immutable dated URL, SHA512 image digest and SHA256 manifest digest. A matching legacy cached image is reused without moving it, since existing virtual disks reference its absolute backing path. Preserve the dated manifest and qcow2 for reconstruction.

`python3 scripts/build-vm.py` creates a 24 GiB virtual qcow2 disk backed by the checked cloud image, serves exact source snapshots and NoCloud seed data through a loopback HTTP server, and boots QEMU TCG. The VM has no host block devices or host filesystem shares. All guest root, `/etc`, `/usr`, package caches, chroots and mount points live in the project-contained virtual disk. Completed outputs are streamed over HTTP PUT to an exact-filename allowlist under `artifacts/vm-build/`, with bounded Content-Length, symlink/escape rejection and atomic `.part` replacement. The host checks the exported ISO digest before declaring a completed build.

The guest runs overlay unit tests, packages `windows12-desktop` twice and compares digests, inspects the Debian package, then builds a Debian trixie amd64 KDE live ISO with live-build and Calamares. The desktop package is installed through `config/packages.chroot` so dpkg tracks its ownership. No arbitrary host source share or host installer is exposed. The ISO is moved into the guest export directory, avoiding a second full copy on the 24 GiB disk. Guest commands refuse execution without the VM marker.

## Outputs and limitations

- Ignored intermediate storage: `.work/builder/` (authenticated packages and metadata, local tools, original cloud image, VM disk, tar source snapshots).
- Ignored outputs: `artifacts/vm-build/` (serial/guest logs, package, ISO if successful, checksums, provenance, exit code).
- A successful build is not a release gate: BIOS and UEFI live boot, disposable VM installation, installed reboot, GUI and service validation are still required; see `VALIDATION.md`.
- This pipeline currently resolves distribution package repositories at build time, so the resulting OS image is not yet byte-for-byte reproducible. The source snapshot, signed repository metadata, package manifest, source lock and output hashes identify the build; frozen Debian snapshot mirrors are still needed for long-term reproducibility.
- Tool bootstrap supports the current amd64 Ubuntu 24.04 build host only. Other hosts need compatible QEMU tools without global installation.
- Debian builder guest boot, filesystem growth, NoCloud seed retrieval and execution of the guest script are observed. Seventeen overlay unit tests passed in the guest. The desktop package was built twice with identical SHA256 `eef6eb901577b2694e44965eaf2a0fe687acf954c45f7feb5777b120a4470b8f`, and dpkg-deb parsed its metadata/contents (7036 bytes). HTTP export successfully preserved this package and logs on an apt failure. The initial apt failure was certificate verification against the managed HTTPS proxy; no TLS checks were disabled. A fresh runner now injects the environment public proxy CA only into the builder and runs update-ca-certificates; target-image cleanup removes that known build CA if inherited. Guest repository/proxy repair, live-build recipe, derivative boot, installer and Office service login remain unverified until logs establish success. There is no ISO yet at this checkpoint.

## Job control and interrupted runs

`python3 scripts/probe-qmp.py status` queries the running VM; `registers` diagnoses CPU state; `quit` stops it without host PID assumptions. QMP uses project-local FIFOs. Managed tool calls have separate PID namespaces, so a PID read from `/proc` may not be signalable from another tool call. The original exec session can also be stopped with its Ctrl-C mechanism.

`python3 scripts/build-vm.py --resume` boots the preserved disk with a fresh NoCloud instance-id, refreshed current proxy port, and the original frozen `checks.tar` whose SHA256 is checked against `build-source.sha256`. It reruns the archived guest build script against cached guest working directories; it is not instruction-level suspend/resume. Changed working-tree sources are not silently mixed into that build. To build changed sources, deliberately preserve the old disk/snapshot and start a new build. Live-build rerun recovery itself remains unverified.

Resume experiment: rebooting the apt-failed builder with a fresh NoCloud instance-id did execute a Linux kernel and cloud-init (QMP CPU evidence) but did not produce resumed serial/build output. It was stopped and preserved for diagnosis. The datasource-name modernization was rolled back to known-working `nocloud-net`, and a fresh CA-equipped builder was launched. Do not count resume recovery as validated. The current HTTP server records request method/path/status (never seed bodies or credentials) in `artifacts/vm-build/http-requests.log`.

The fresh CA-equipped guest successfully fetched signed Debian repository indexes and installed live-build/debootstrap through the managed proxy with TLS verification enabled. Before committing to the full desktop build, the virtual root budget was increased to 24 GiB and live-build retained package/stage caches disabled (`--cache false`); compressed ISO export is a move within the guest, not a second copy. The desktop package and log now export immediately after package validation, before lengthy OS-build work, while final `build.exit` is still exported only by the exit trap.

## Separate ISO inspection tools

`python3 scripts/build-tools.py --profile iso` prepares xorriso and dependencies in `.work/builder/iso-tools/` and records `build/iso-tools-lock.json`. This path is deliberately separate from the active QEMU tools; never overwrite an executable or library currently mapped by a running VM. The ISO tool profile completed using the same authenticated Ubuntu metadata, and xorriso/libisofs/libburn/libisoburn 1.5.6 startup was verified. Runtime library path: `.work/builder/iso-tools/usr/lib/x86_64-linux-gnu`. Actual image extraction remains pending an ISO.

The dependency resolver selects the highest Debian-versioned candidate, verifies selected dependency version constraints, handles versioned `Provides` for Ubuntu t64 transitions, and refuses ambiguous virtual providers rather than guessing. Downloaded archive names are deduplicated before parallel downloads.

The runner now takes a nonblocking lifetime `flock` on `.work/builder/runner.lock`. It also probes preexisting QMP controls to detect an older runner that did not take the lock. A responding VM or an uncertain live listener blocks launch before source snapshots/provenance/controls are changed. These guards do not change the already running source-build process.

## Observed workspace synchronization resource issue

During the running build, regular files named `.build.qcow2.<randomsuffix>` and recursively suffixed variants accumulated under the project working directory. They consumed over10GiB while the configured build disk was under1GiB. QMP reported only `build.qcow2` and its Debian backing image as attached files. Process FD details were inaccessible, so platform implementation details and inode ownership of synchronization writers are not proven. Parallel/frequent filesystem tool invocations correlated with the accumulation; this is an observation, not a confirmed explanation of platform internals.

The narrowly bounded cleanup `python3 -B scripts/build-clean-sync.py --apply` removed42 regular temporary copies older120s whose metadata remained unchanged, excluding symlinks and configured-image inodes. It reclaimed11,228,225,536 observed free bytes. Names, sizes, allocated bytes and modification times are recorded in `.work/builder/sync-temp-cleanup.jsonl`. The helper audits without deletion when `--apply` is omitted. It never targets configured images or general `.qcow2` files.

Avoid parallel or rapid new filesystem exec calls while a live disk changes. Prefer one persistent `python3 -u -B scripts/build-monitor.py` session and poll its existing stdout at intervals of at least60s. It records bounded progress/resource summaries under the project; stdin `cleanup` invokes the same reviewed cleanup from inside that session, `status` requests a snapshot, and `stop` stops only the monitor. Whether this fully prevents synchronization-copy growth remains to be measured. If copies cannot be bounded safely, preserve configured disks and report the environment resource blocker instead of risking disk exhaustion.

Unattended safeguard: launch `python3 -u -B scripts/build-monitor.py --auto-cleanup` in a TTY-backed tool session (`tty=true` is required for interactive stdin; non-TTY monitoring still works but stdin may be closed). The monitor runs the same reviewed >120-second cleanup every60s. If cleanup cannot retain6GiB free, it requests QMP `stop` for the main guest CPUs and writes `.work/builder/paused-state.json` plus an audit entry in `pause-events.jsonl`. This pauses only the project VM; it does not quit the VM or alter the host. It never auto-resumes. Confirm actual QMP status before explicit `python3 -B scripts/probe-qmp.py resume --reason 'space issue resolved'`; a low-space condition can pause it again. QMP clients use a serialized project-local lock. Pause behavior is implemented but has not been triggered on the healthy main build; read-only status and automatic cleanup were verified.

Monitor tool session handles are agent-scoped. An unknown handle in a replacement agent does not establish that the process stopped; reconcile QMP and files before launching anything. The same-session TTY cleanup command was verified and restored ample space, but copy growth continued during otherwise quiet monitoring; automatic cleanup is necessary in this environment. Helpers skip disappearing temporary names to tolerate synchronization races. Current monitored automatic cycles reclaim generated copies and maintain roughly25GB free while the real disk is around2GB; this does not prove the larger final build/export peak will fit.

Guard logging is best-effort: inability to append monitor.log cannot prevent a low-space QMP pause, and malformed/empty pause markers are reported without terminating monitoring. Pause markers are replaced atomically where space permits. A successful QMP pause/resume is still reported as successful if marker/audit storage fails, with an explicit stdout warning to reconcile actual VM state. This addresses ENOSPC ordering by inspection; no disk-filling test or healthy-guest pause was performed.

## Interrupted live-build assessment

Read-only inspection of the exact installed live-build20250505+deb13u1 package shows that `lb config` preserves completed `.build` markers; `bootstrap_debootstrap` skips a completed bootstrap. An interrupted `chroot_install-packages` keeps `chroot/root/packages.chroot` until apt succeeds, and normal lock traps remove the active `.lock`. Exit cleanup unmounts chroot filesystems and removes only the matching mount-stage markers.

However, `Save_package_cache` explicitly purges `chroot/var/cache/apt/archives/*.deb` when `LB_CACHE=false`. SIGTERM/EXIT cleanup invokes it. Gracefully interrupting the current archive-download phase could therefore discard hundreds of completed downloads even though the root filesystem and completed stages remain. No controlled shutdown was performed at this point; a test after the package-install stage succeeds would preserve the expensive completed stage. Preserving package archives on interrupted downloads is a future cache-policy improvement, not verified recovery behavior.

The frozen recipe does not pass `--apt-http-proxy`; the saved `LB_APT_HTTP_PROXY` value therefore stays empty. Exact live-build source derives and exports `http_proxy` during validation without persisting that derived value to `LB_APT_HTTP_PROXY`. A replay should use the freshly injected builder apt proxy and environment proxy, which must agree; chroot execution explicitly forwards fresh `http_proxy` and `no_proxy`. No chroot apt proxy configuration is generated by that mechanism. Future explicit CLI proxy settings would need resetting/overriding because saved configuration is loaded before CLI overrides and conflicting proxy sources cause validation failure. Actual full-build replay still must check the reported new proxy port and skipped bootstrap/stages.
